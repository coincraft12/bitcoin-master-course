# lesson-51 · 12-3 기관 커스터디와 볼트 설계

## 목표
- 개인 보관과 기관 보관의 위협·요구사항 차이를 설명한다 (s123-diff).
- 멀티시그·MPC·Taproot 방식을 보안·운영·규제 관점에서 비교한다 (s123-compare).
- 키 분산과 서명 정책을 포함한 볼트 설계서를 작성한다 (s123-policy, s123-vault, s123-lab).

|---|---|---|---|
| 온체인 모습 | 조건이 드러남(P2WSH) / 쓴 리프만(Tapscript) | 단일 서명 | 단일 서명 (평시) |

2-of-3 볼트 예시(s123-vault)

| 키 | 보관자 | 장소 | 장비 |
|---|---|---|---|
| A | 대표이사 | 본사 금고 | 제조사 X 하드웨어 지갑 |
| B | 재무책임자 | 다른 도시 지점 금고 | 제조사 Y 하드웨어 지갑 |
| C | 외부 수탁 파트너 또는 은행 대여금고 | 제3의 장소 | 제조사 Z 또는 종이 백업 |

평시 출금 A + B · A 부재 시 B + C · 디스크립터 사본은 세 장소 모두에(4-5) · 확장: 1년 미사용 시 별도 복구 키가 열리는 타임락 리프(6-5, 12-4).

## 파일
- `vault_design_template.md` — 실습 설계서 양식 8항목 (s123-lab). 영상 밖 과제, 25분
- `vault_descriptor.sh` — 설계서 06항 확인: 6-2·6-5 문법 디스크립터 초안 두 개를 regtest 감시 지갑으로 가져와 주소를 만들고, A+B·B+C 출금(그리고 원하면 복구 키 단독 출금)을 리허설한다

## 준비
`bash env/setup_regtest.sh`. 6-2에서 만든 `participant_1~3` 지갑과 `xpub_1~3.txt`를 A·B·C로 쓴다. 파일이 있는 폴더에서 실행하거나 `XPUB_DIR=폴더`로 알려 준다. 없으면 스크립트가 6-2 s62-lab1과 같은 방법으로 만든다. 복구 키 R은 새 지갑 `vault_recovery`.

## 실행
```bash
bash part5/lesson-51/vault_descriptor.sh                 # OLDER=52560 (약 1년). 복구 리허설은 건너뜀
OLDER=20 bash part5/lesson-51/vault_descriptor.sh        # 복구 리프를 20블록으로 줄여 R 단독 출금까지
```
초안 두 개
```
wsh(sortedmulti(2,A/0/*,B/0/*,C/0/*))                                         # 6-2 문법
tr(NUMS,{multi_a(2,A/0/*,B/0/*,C/0/*),and_v(v:pk(R/0/*),older(52560))})      # 6-5 문법, 키 경로 없음
```
NUMS는 6-5의 `50929b74…3ac0`. 내부키가 NUMS라 키 경로로는 아무도 혼자 쓸 수 없다 → 결정 원칙 "한 사람 단독 불가". 평시 지출이 단일 서명처럼 보이길 원하면 내부키를 `musig(A,B)`로 바꾸는 설계(키 경로 2-of-2 MuSig2, Core 31 지갑 서명)도 있다 — 14-4 최종 프로젝트에서 다룬다.

## 기대 출력
디스크립터의 tpub·체크섬, 주소, txid는 실행마다(참여자 지갑마다) 다름. 이 환경에는 노드가 없어 문법 검사(`bash -n`, shellcheck)까지만 했다. witness 바이트 수는 스크립트 구조에서 정해진다.
```
== 초안 ① wsh(sortedmulti) — 6-2 문법 ==
wsh(sortedmulti(2,[지문8자/84h/1h/0h]tpub…/0/*,…,…))#체크섬8자   (실행마다 다름)
[true,true]
첫 주소: bcrt1q… (P2WSH, 실행마다 다름)
== 초안 ② tr(NUMS, {2-of-3 CHECKSIGADD, 복구 키 + older(52560)}) — 6-5 문법 ==
tr(50929b74c1a04954b78b4b6035e97a5e078a5a0f28ec96d547bfee9ace803ac0,{multi_a(2,…),and_v(v:pk(…),older(52560))})#…
[true,true]
첫 주소: bcrt1p… (P2TR, 실행마다 다름)
== 평시 출금: A + B (participant_1, participant_2) ==
9a1f…txid (실행마다 다름)
[0,64,64,104,65]
== A 부재 시: B + C (participant_2, participant_3) ==
…txid (실행마다 다름)
[64,64,0,104,65]
```
- witness는 `[C 서명|빈 값, B 서명|빈 값, A 서명|빈 값, 리프 스크립트 104B, 컨트롤 블록 65B]`. 서명은 키 순서의 **역순**으로 놓인다(스택 맨 위가 A). 서명하지 않은 키 자리는 빈 값.
- 리프 스크립트 104B = `<A> CHECKSIG <B> CHECKSIGADD <C> CHECKSIGADD 2 NUMEQUAL` (33+1+33+1+33+1+1+1). 컨트롤 블록 65B = 1 + NUMS 32 + 복구 리프 해시 32 → 복구 키 R은 체인에 드러나지 않는다.
- `OLDER=20`이면 마지막에 `[64,37,65]`(R 서명, `<R> CHECKSIGVERIFY 20 CSV` 37B, 컨트롤 블록)가 하나 더 나온다.

## 흔히 막히는 지점
- `getdescriptorinfo` 체크섬을 붙이지 않고 `importdescriptors` → 실패. 스크립트는 `with_checksum`으로 붙인다.
- 같은 키를 한 리프에 두 번 넣으면 `multi_a`가 거부한다. 참여자마다 다른 지갑을 쓴다.
- 이미 만든 `vault_tr_52560` 지갑이 있으면 다시 만들지 않고 그대로 쓴다. 처음부터 하려면 `env/reset_regtest.sh`.
- 정책이 복잡할수록 지갑 소프트웨어가 그 리프로 서명·완성할 수 있는지 리허설로 확인한다(12-4).
