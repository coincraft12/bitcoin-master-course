# lesson-53 · 13-1 라이트닝 네트워크 원리

## 목표
- 결제 채널의 개설·상태 갱신·종료 과정을 설명한다 (s131-channel).
- 오래된 상태를 제출하면 처벌받는 구조(취소 키)를 설명한다 (s131-penalty).
- HTLC로 다중 홉 결제가 신뢰 없이 성립하는 원리를 설명한다 (s131-htlc).

이 차시에는 코드 실습이 없다. 13-2(lesson-54)의 regtest 실습에서 아래 원리를 실제 명령 결과로 확인한다.

## 정리
결제 채널 (s131-channel)
1. **개설** — 앨리스와 밥이 2-of-2 멀티시그 출력(6-2)에 자금을 넣는 펀딩 트랜잭션을 블록에 기록
2. **상태 갱신** — "현재 잔액 분배" 커밋먼트 트랜잭션에 서로 서명해 주고받되 블록에는 올리지 않는다. 결제마다 새 분배로 다시 서명
3. **종료** — 마지막 상태를 블록에 올려 정산

수천 번 결제해도 블록에 남는 것은 개설·종료 두 번뿐. 펀딩 트랜잭션이 블록에 들어가기 전에 첫 커밋먼트에 미리 서명해야 하므로 txid가 바뀌면 안 된다 → 가변성 해결(5-2)이 전제.

처벌과 워치타워 (s131-penalty)
- 상태를 갱신할 때마다 이전 상태를 무효화하는 비밀(취소 키)을 상대에게 넘긴다.
- 각자의 커밋먼트에서 "자기 몫"은 상대 타임락(6-3) → 바로 못 가져간다.
- 예전 상태를 올리면 상대가 대기 기간 안에 취소 키로 채널 자금 전부를 가져간다.
- 대신 감시 의무 → 오프라인일 때 대신 감시하는 워치타워. 대기 기간 안에 처벌 트랜잭션을 확정시켜야 하므로 수수료 인상 수단(8-4, 8-5)이 보안의 일부다.

HTLC = 해시락 + 타임락 (s131-htlc)
```
"비밀 R의 해시가 H인 그 R을 보여주면 받는다"        (해시락)
"정해진 시간까지 못 보여주면 보낸 쪽이 돌려받는다"   (타임락)
```
| 단계 | 내용 |
|---|---|
| 1 인보이스 | 캐럴이 비밀 R을 만들고 H를 앨리스에게 |
| 2 앨리스 → 밥 | "R을 보여주면 1,001 sat" · 타임락 길게 |
| 3 밥 → 캐럴 | "R을 보여주면 1,000 sat" · 타임락 짧게 |
| 4 캐럴이 R 공개 | 밥에게서 받는다 |
| 5 밥도 R로 | 앨리스에게서 받는다 · 1 sat = 라우팅 수수료 |

타임락이 뒤로 갈수록 짧은 이유: 밥이 캐럴에게 내준 뒤에도 앨리스에게서 받을 시간 여유가 있어야 한다. R 공개 = 결제 영수증 → lesson-54 `check_preimage.py`로 `SHA256(preimage) = payment_hash`를 직접 확인한다.

라우팅·유동성·규모 (s131-routing): 양파 라우팅(중간 노드는 바로 앞·뒤만 안다), 채널 방향별 잔액 한계(받기만 하는 상점은 들어오는 유동성 필요), 중간 잔액 부족 시 경로 재시도. 공개 용량 약 4,900 BTC(2026년 5월, 2025년 12월 사상 최고 약 5,637 BTC), 약 17,400 노드·41,000 채널(노드 수는 2022년 정점 약 2.07만보다 감소). 모바일·기업용 비공개 채널은 공개 통계에 잡히지 않는다.

한계와 트레이드오프 (s131-limits): 온라인·감시 필요(워치타워로 완화), 채널 개설·종료에 온체인 수수료, 큰 금액·유동성 문제, 수수료 급등기의 강제 종료(미리 서명된 커밋먼트의 수수료 → 8-4 앵커·CPFP, 8-5 TRUC·패키지 릴레이).

## 흔한 오해 (s131-myth)
- 라이트닝은 별도 코인·블록체인이다 → 비트코인 트랜잭션을 체인 밖에서 주고받는 프로토콜이다.
- 라이트닝 결제는 덜 안전하다 → 보안 모델이 다르다. 비수탁이면 최종적으로 온체인 정산 권리를 가진다.
- 중간 노드가 결제 금액을 가로챌 수 있다 → 비밀 R 없이는 받을 수 없고, 받으려면 R을 공개해야 한다.
