# lesson-55 · 13-3 사이드체인과 페더레이션, 2026 Liquid 사고

## 목표
- 비트코인을 "옮긴다"는 말의 실제 구조(잠금과 대응 자산 발행)를 설명한다 (s133-peg).
- 사이드체인·페더레이션·eCash·래핑 BTC의 신뢰 가정을 비교한다 (s133-compare, s133-ecash).
- 브리지 보안을 평가하는 핵심 질문을 적용한다 (s133-questions).

옮긴다 = **잠그고, 대신 발행한다**: ① 페그인(조건 있는 출력에 BTC를 잠금) ② 발행(다른 시스템에서 같은 양의 대응 자산) ③ 페그아웃(대응 자산 소각 → 잠긴 BTC 해제). 대응 자산의 가치는 "잠긴 비트코인을 누가, 어떤 조건으로 풀 수 있는가"에 달려 있다.

| 방식 | 잠긴 BTC를 푸는 주체 | 장점 | 신뢰 가정·위험 |
|---|---|---|---|
| 단일 수탁 래핑 | 수탁 기관 | 다른 체인 생태계에서 활용 | 수탁자 파산·동결·변심, 수탁 구조 변경 |
| 페더레이션 사이드체인 (예: Liquid) | 다수 기관의 멀티시그 정족수 (11-of-15) | 빠른 블록, 기밀 거래 | 정족수 이상 담합·장애, 검증 소프트웨어 결함 |
| 페더레이션 eCash (예: Fedimint, Cashu) | 민트 운영자 (단일 또는 연합) | 블라인드 서명으로 높은 프라이버시 | 운영자에 자금 수탁 |
| 드라이브체인 제안 (BIP300/301) | 비트코인 채굴자 | 다양한 사이드체인 실험 | 채굴자 권한 확대 우려, 소프트포크 필요, 활성화 합의 없음 |
| BitVM 계열 브리지 | 참여자 중 정직한 1명만 있으면 | 신뢰 가정 크게 축소 | 복잡도, 유동성·운영 비용 (13-4) |

2026년 9월 6일 Liquid 사고(s133-liquid): 소프트웨어(Elements) 결함으로 담보 없는 L-BTC가 유효한 페그아웃으로 처리 → 준비금 약 4,200 BTC 중 약 3,998.5 BTC 유출. 키는 하나도 탈취되지 않았다. 약 3,400 BTC 반환, 나머지는 Blockstream이 1:1 페그 보전 약속. 9월 중순 기준 페그인·아웃 중단. 교훈: "누가 키를 갖나"만으로는 부족하다 → "누가, 어떤 소프트웨어로, 무엇을 검증하고 서명하나".

브리지 평가 질문 다섯 가지(s133-questions)
1. 잠긴 BTC를 푸는 주체는 누구이며 몇 명인가?
2. 그중 몇 명이 담합하면 자금을 가져갈 수 있는가?
3. 운영자가 사라지거나 협조하지 않으면 사용자가 스스로 BTC를 되찾을 수 있는가?
4. 운영 주체·키 보관 구조·검증 소프트웨어가 공개·검증 가능한가?
5. 규제·법적 압력으로 동결될 수 있는가?

## 파일
- `reserve_check.py` — 슬라이드의 `scantxoutset` 명령을 감싼 스크립트. 주소 형식·네트워크 검사, 잔액 합계, 공시 수치와의 차이(만분율까지)
- `example_addresses.txt` — 연습용 주소 목록(BIP84 문서의 공개 테스트 벡터 주소. 실제 기관 주소가 아니다)

## 실습 (s133-questions)
래핑 BTC나 사이드체인이 공시한 보유 주소 목록을 가져와 내 노드로 잔액 합계를 확인하고 공시 수치와 비교한다. 메인넷 노드 필요(노드가 없으면 블록 탐색기로).
```bash
bitcoin-cli scantxoutset start '["addr(<공시된 보유 주소 1>)", "addr(<주소 2>)"]' | jq .total_amount
```
파이썬으로:
```bash
python part5/lesson-55/reserve_check.py 공시주소.txt --disclosed <공시 BTC>
python part5/lesson-55/reserve_check.py part5/lesson-55/example_addresses.txt --dry-run     # 노드 없이 명령만
```
결과를 "누가 풀 수 있나"(위 질문 1~5)에 대한 답과 함께 한 단락으로 정리한다. 이 질문들은 13-4의 L2 평가 체크리스트로 이어지고, 14-4 실습(ETF·기업 공개 주소 확인)에서 같은 스크립트를 다시 쓴다.

## 기대 출력
`--dry-run` (결정적, 직접 실행해 확인)
```
$ python part5/lesson-55/reserve_check.py part5/lesson-55/example_addresses.txt --dry-run
주소 2개 형식 확인 완료
bitcoin-cli scantxoutset start '["addr(bc1qcr8te4kr609gcawutmrza0j4xv80jy8z306fyu)", "addr(bc1qnjg0jd8228aq7egyzacy8cys3knf9xvrerkf9g)"]' | jq .total_amount
```
메인넷 노드에서 공시 주소 목록으로 (형태 예시 — 이 작성 환경에는 노드가 없어 숫자는 설명용 예시다. 실제 값은 대상과 조회 시점마다 다름)
```
주소 12개 형식 확인 완료
UTXO 12개, 높이 971204   (예시 · 실행마다 다름)
내 노드가 센 잔액 합계: 3998.50000000 BTC   (예시 · 실행마다 다름)
공시 수치            : 4000.00000000 BTC
차이 −1.50000000 BTC (−0.03%)
→ "이 BTC를 누가, 어떤 조건으로 풀 수 있나"(키 보유 주체·정족수·검증 소프트웨어)와 함께 한 단락으로 정리한다.
```
마지막 줄의 차이 계산(`compare()`, 정수만 사용)은 3,998.5 vs 4,000 BTC를 넣어 직접 실행해 확인한 출력이다.

## 흔히 막히는 지점
- 오래 걸린다 — `scantxoutset`은 UTXO 집합 전체를 훑는다. 다른 창에서 `bitcoin-cli scantxoutset status`로 진행률을 본다.
- 프루닝 노드도 된다(UTXO 집합만 쓴다). 아직 동기화 중이면 그 높이 기준 값이다 → 출력의 높이를 함께 적는다.
- 주소 접두어가 네트워크와 다르면 스크립트가 거부한다(`bc1…`은 메인넷, `bcrt1…`은 regtest).
- 공시가 주소를 일부만 밝혔다면 합계가 공시보다 작은 것이 정상이다 — "공개 범위"도 평가 정보다.
