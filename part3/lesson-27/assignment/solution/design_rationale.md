# 설계 근거 (예시 1쪽) — 상속형 Taproot 지갑

> 6강 미니 과제 03 작성 예. 키는 자리표시(공개 테스트 니모닉)다. 실제 설계는 12-4에서 이어서 한다.

## 1. 구조
```
tr( 평소 키 = 2-of-2 MuSig2 집계키(본인 + 공동 서명자),
    { 비상 리프 = and_v(v:pk(복구 키), older(52560)) } )
```

## 2. 왜 이 조건을 키 경로에 두었나
- 평소 지출이 가장 잦다 → 가장 싼 길(서명 64B 하나, 스크립트·컨트롤 블록 없음)에 둔다(6-5 "자주 쓰는 조건은 얕게, 가장 잦은 것은 키 경로로").
- 키 경로 지출은 단일 서명 지갑과 똑같이 보여 비상 리프가 있다는 사실조차 드러나지 않는다(6-4 약속).
- MuSig2는 n-of-n이라 한 명이 없으면 키 경로를 못 쓴다 → 그래서 비상 리프가 필요하다(7-4 s74-caveat).

## 3. 왜 이 조건을 리프에 두었나
- 복구 키 단독 + 1년 상대 타임락: 평소엔 절대 쓰이지 않아야 하는 길이다. 쓰이는 순간에만 리프 39B와 컨트롤 블록 33B가 공개된다.
- 상대 타임락(CSV)이라 코인을 받을 때마다 1년이 새로 시작된다. 주인이 살아 있으면 1년 안에 한 번씩 키 경로로 자기에게 옮겨(리프레시) 복구 경로를 계속 닫아 둔다.
- 절대 타임락(CLTV)을 쓰면 정해진 날짜가 지나면 언제든 복구 키가 쓸 수 있어 "오래 안 쓰면"이라는 상속 의도와 맞지 않는다.

## 4. 타임락 상한 확인
- nSequence 상대 타임락 값은 하위 16비트 → 최대 65,535블록(약 455일). 52,560블록(약 365일) ≤ 65,535 ✓
- 지출 트랜잭션은 version 2 이상, 해당 입력 nSequence = 52,560 (블록 단위, 22번 비트 0).

## 5. 복구 키트에 무엇을 남기나 (4-5, 6-2 "디스크립터가 복구 정보 전부")
- 공개 디스크립터 전체(체크섬 포함) — 모든 키 보관 장소에 함께. 리프 내용과 내부키를 모르면 복구 지출의 컨트롤 블록을 만들 수 없다.
- 복구 키의 니모닉(또는 하드웨어 지갑) — 상속인 쪽에만.
- 절차 메모: "마지막 지출 후 52,560블록이 지난 뒤, Core에 디스크립터를 가져와 PSBT 생성 → 복구 키로 서명". 생성 높이·대략의 날짜를 함께 적는다.
- 하지 않을 것: 니모닉과 디스크립터를 한 장에 같이 두지 않는다.
