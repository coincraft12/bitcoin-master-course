# lesson-03 · 1-3 트랜잭션 하나의 일생: 송금 버튼부터 확인까지

1부 기초 · 1강 비트코인 개요와 동작 원리

## 목표

- 송금 버튼부터 확정까지 6단계를 순서대로 설명할 수 있다
- 탐색기에서 미확정, 확인 수, 수수료율을 읽을 수 있다
- 각 단계를 깊게 다루는 강을 연결할 수 있다

## 트랜잭션의 6단계

| 단계 | 하는 일 | 깊게 다루는 곳 |
|---|---|---|
| 1 만들기 | 지갑이 쓸 코인을 고르고 받는 출력, 잔돈, 수수료를 정한다 | 3~5강 |
| 2 서명 | 개인키로 서명한다. 이후 한 글자도 바꿀 수 없다 | 7강 |
| 3 전파 | 노드가 검증한 뒤 이웃 노드에 퍼뜨린다 | 9강 |
| 4 멤풀 | 노드마다 있는 대기실. 수수료율이 높은 것부터 뽑힌다 | 8강 |
| 5 블록 포함 | 채굴자가 퍼즐을 풀면 블록에 담긴다. 1 확인 | 10~11강 |
| 6 확인 누적 | 위에 블록이 쌓일수록 되돌리기 어렵다 | 10-3 |

## 실습 A (슬라이드 LAB): 실제 트랜잭션 하나 따라가기 — 공개 탐색기

mempool.space 같은 공개 탐색기로 진행합니다.

| 단계 | 할 일 |
|---|---|
| 1 | 탐색기의 멤풀 화면에서 수수료율 띠를 보고 다음 블록에 들어갈 구간을 확인한다 |
| 2 | 미확정 트랜잭션 하나를 골라 txid, 수수료율, 예상 대기 시간을 기록한다 |
| 3 | 몇 분 뒤 다시 조회한다. 안 들어갔다면 수수료율로 이유를 설명한다 |
| 4 | 블록 170의 첫 P2P 송금을 조회해 입력 1개, 출력 2개를 확인한다 |

### 활동지

| 항목 | 기록 |
|---|---|
| txid | ________ |
| 수수료율 (sat/vB) | ________ |
| 최초 조회 시각 | ________ |
| 포함 블록 높이 | ________ |
| 확인 수 | ________ |

4단계: 탐색기에서 블록 높이 170을 열면 트랜잭션이 2개 있습니다. 첫째는 코인베이스이고, 둘째가 첫 P2P 송금입니다. 입력 1개, 출력 2개(지급과 잔돈)를 확인하세요. 이 트랜잭션은 5강에서 바이트 단위로 다시 만납니다.

## 실습 B: 같은 일생을 내 regtest 노드에서 따라가기

2강에서 표준 환경을 만든 뒤([env/README.md](../../env/README.md)) 같은 흐름을 내 노드에서 반복합니다. alice가 bob에게 0.1 BTC를 보내고, 멤풀 → 블록 포함 → 6 확인까지 따라갑니다.

```bash
env/setup_regtest.sh        # 아직 안 했다면
part1/lesson-03/lab.sh
```

| lab.sh 구간 | 단계 | 쓰는 RPC |
|---|---|---|
| 만들기·서명·전파 | 1~3 | `sendtoaddress`(지갑이 코인 선택·서명·노드에 제출), `getrawtransaction` |
| 멤풀 | 4 | `getrawmempool`, `getmempoolentry`(vsize, 수수료), `gettransaction`(확인 수 0) |
| 블록 포함 | 5 | miner가 `-generate 1` → 확인 수 1, 멤풀에서 빠짐 |
| 확인 누적 | 6 | `-generate 5` → 확인 수 6 |

regtest는 나 혼자의 네트워크라 3단계 전파(이웃 노드)는 일어나지 않고, 블록은 채굴자를 기다리지 않고 명령으로 즉시 만듭니다.

### 기대 출력

새로 만든 표준 환경에서 처음 실행한 예입니다. txid, 블록 해시, 블록 높이는 실행마다 다릅니다. vsize와 수수료는 지갑 주소 유형과 코인 구성에 따라 달라질 수 있습니다.

```
[만들기·서명·전파] txid: c9092aec23dc0e6d76b526490bc1c935bf2ff51af771c07757e460d01f3aa24b
{
  "vin_count": 1,
  "vout_count": 2,
  "vsize": 141
}
[멤풀] 멤풀에 있는가: true
{
  "vsize": 141,
  "fee_btc": 0.00002820,
  "feerate_sat_per_vb": 20
}
[멤풀] 확인 수: 0
{
  "confirmations": 1,
  "blockheight": 103,
  "blockhash": "af58a55ccc4618c77a47851b7f9e7ddf35e3cbda8121d4f8574c75600307fcad"
}
[블록 포함] 멤풀에 남아 있는가: false
[확인 누적] 확인 수: 6
```

(txid·블록 해시·블록 높이는 실행마다 다름)

- 출력이 2개인 이유: bob에게 가는 0.1 BTC와 alice에게 돌아오는 잔돈입니다(1-4).
- 수수료율 20 sat/vB는 `bitcoin.conf`의 `fallbackfee=0.0002`(BTC/kvB)에서 나옵니다. regtest에는 수수료 추정 데이터가 없기 때문입니다.
- 6 확인은 담긴 블록 위로 블록이 5개 더 쌓인 상태입니다. 담긴 블록 자신이 1 확인입니다.

## 흔히 막히는 지점

- **실습 A: 고른 트랜잭션이 너무 빨리 확정되어 미확정 상태를 관찰하지 못함.** 수수료율이 낮은 쪽에서 다시 고르세요.
- **탐색기마다 같은 트랜잭션의 상태가 다르게 보임.** 노드마다 자기 멤풀이 있고 내용이 조금씩 다르기 때문입니다(전파 시점, 정책, 메모리 한도).
- **실습 B: `sendtoaddress`가 수수료 추정 실패 오류.** `bitcoin.conf`의 `[regtest]` 아래 `fallbackfee`를 확인하세요.
- **실습 B: `Insufficient funds`.** alice 잔액이 부족합니다. `env/setup_regtest.sh`를 다시 실행하거나 `env/reset_regtest.sh` 후 다시 만드세요.

## 핵심 확인 질문

- 송금 버튼을 누른 뒤 10분 동안 그 돈은 어디에 있나요? (서명된 트랜잭션의 형태로 네트워크에 퍼져 각 노드의 멤풀에서 기다린다)
- 6 확인이면 "약 1시간"인 이유와, 그것이 규칙이 아니라 관행인 이유는?
- 블록에 한 번 들어간 트랜잭션도 다시 미확정이 될 수 있는 경우는? (재조직, 10-3)
